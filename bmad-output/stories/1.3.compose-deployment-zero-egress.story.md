# 1.3: Compose deployment with zero egress

**Story ID:** 1.3
**Epic:** 1 — Platform Foundation & Model Selection
**Slug:** compose-deployment-zero-egress
**Status:** ready-for-dev

## Story

As the **builder**,
I want **the whole stack to start with one command on the Azure UAT VM, with only HTTPS on port 8043 exposed and no internet route**,
so that **every later feature is deployed into a confidential-by-default environment**.

## Acceptance Criteria

1. `docker compose -f deploy/compose.yml up -d` starts: `caddy`, `api`, `worker`, `postgres` (PostgreSQL 18 + pgvector image), `valkey` (Valkey 8) and a one-shot `migrate` service (`alembic upgrade head`) that must succeed before `api`/`worker` start.
   - **Only `caddy` publishes a host port: `8043`.**
   - Networks `app`, `inference` and `parsing` are declared `internal: true`.
2. Caddy serves the built SPA as static files and reverse-proxies `/api/*`, `/healthz` and `/readyz` to `api:8000`. It sets:
   - TLS (internal CA via `tls internal`, or a certificate path when provided), with HSTS
   - CSP `default-src 'self'; img-src 'self' data:; connect-src 'self'; frame-ancestors 'none'`
   - `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`
   - a request-body limit of 50 MB
3. The Postgres init script creates the roles `app_migrator` (owns the schema, DDL) and `app_rw` (DML only; **`NOBYPASSRLS`**, not the table owner). `postgresql.conf` sets a minimal `wal_keep_size` and no WAL archiving. The data directory is bind-mounted from `/data/postgres`.
4. Secrets come only from Compose `secrets:` (files under `/etc/foundry/secrets/`, plus the KEK at `/etc/foundry/kek`), mounted into `/run/secrets`.
   - `deploy/env.example` lists non-secret settings only.
   - No secret appears in any compose file, image or `.env`.
5. `compose.yml` uses `include:` for `compose.inference.yml`, `compose.parser.yml` and `compose.observability.yml` (profile `observability`). This story creates them as **valid placeholders** (`services: {}`) for Stories 1.4, 9.2 and 7.10 to fill.
6. The runbook `deploy/runbook.md` (v0) documents:
   - host prep: Docker `data-root` at `/data/docker` via `deploy/host/daemon.json`; **never use `/mnt`** (ephemeral Azure temp disk); verify NSG outbound deny + optional nftables default-deny
   - the offline image load procedure (`docker load` + SHA-256 check)
   - start/stop, the secret/KEK file locations and permissions (0400 root)
   - the interim backup location `/data/backups`
7. `deploy/host/verify-egress.sh` runs from inside the `api` and `worker` containers. It **passes only if** outbound connections to a public IP and a public DNS name both fail, and `postgres` and `valkey` are reachable.

## Dev Notes

- **Topology:** only Caddy is exposed; app, inference and parsing networks are internal;
  the parser has no network except `parsing`. [Source: architecture.md#ADR-034]
- **Port:** the inbound range on the VM is 8000–8050, so **Caddy listens on 8043**.
  Ports 8000–8050 must not be bound by anything else on the host. [Source: architecture.md#ADR-034] [Source: decision-log.md#2026-10-07--port-8043-interim-local-backups]
- **Azure host facts:**
  - outbound internet is already blocked at the Azure network level (host firewall is defence in depth);
  - Docker data-root goes on persistent `/data` (the root disk is 62 GB);
  - `/mnt` is the ephemeral temp disk and **must hold no content**;
  - disks have default Azure SSE.

  [Source: architecture.md#ADR-034] [Source: architecture.md#ADR-028] [Source: decision-log.md#2026-10-07--host-specs-verified-nbfcuatyolomlapp01]
- CSP and rendering rules (no external images or URLs) back up the output-gate stripping. [Source: architecture.md#ADR-025]
- **DB roles:** `app_rw` must be subject to RLS. That means no `BYPASSRLS` and not the
  table owner, because owners bypass RLS unless `FORCE` is set; later migrations use
  `FORCE` too. Audit tables grant `app_rw` INSERT/SELECT only (Story 7.1). [Source: architecture.md#ADR-023] [Source: architecture.md#ADR-005]
- WAL kept minimal with no archiving, to bound how long deleted ciphertext lingers. [Source: architecture.md#ADR-035]
- **KEK:** a root-only file on the OS disk, `/etc/foundry/kek` (0400), mounted as a
  Compose secret, never in DB backups. No Key Vault. [Source: architecture.md#ADR-028] [Source: decision-log.md#2026-10-07--azure-uat-host-no-key-vault-default-azure-disk-encryption]
- **Interim backups** go to `/data/backups` (2-day retention, Story 7.5); document the
  location now. [Source: architecture.md#ADR-035]
- **Offline updates:** images and models arrive by `docker save`/`load` with checksum
  verification. No code may assume internet access. [Source: architecture.md#ADR-034]
- Compose `include:` needs Docker Compose ≥ 2.20 (record the installed version in the runbook). [Inference]
- Upload limit 50 MB matches FR-042. [Source: prd.md#FR-042]

## Testing

  - AC #1 → `docker compose ps` shows all services healthy; `docker compose port` shows only `caddy 8043`; `migrate` exited 0.

- **Edge cases:** Docker running with the default data-root on `/` (the runbook check must fail loudly); `migrate` failing (api must not start).

- **Decisions / deviations:**
  - **DB passwords without env vars:** `backend/docker-entrypoint.sh` (an extra file) writes a 0600 pgpass in tmpfs (`/tmp/pgpass`, `PGPASSFILE`) from the secret files. DB URLs in compose carry no password. It also dispatches `api` / `worker` / `migrate`. Until Story 1.11, the worker is a placeholder that sleeps, and its healthcheck only checks that `import app` works.
  - **Secret ownership:** host files stay `0400 root`. Compose's long-syntax `uid`/`gid`/`mode` copies them into the container as 10001 (app) or 999 (postgres). This needs `docker compose` to run as root on the VM.
  - **Extra secret `db_superuser_password`:** the postgres image requires one. The superuser is socket-only afterwards, via an added `deploy/postgres/pg_hba.conf` where the app roles use SCRAM over `samenet`.
  - **Init script:**
    - It creates `vector` and `citext` as superuser, because pgvector is **not** a trusted extension (checked in the image). The baseline migration's `IF NOT EXISTS` is then a no-op.
    - Default privileges give `app_rw` SELECT/INSERT/UPDATE/DELETE on tables created by `app_migrator`. **Story 7.1 must REVOKE UPDATE, DELETE on `audit_events`.**
  - **Upload limit:** Caddy's `max_size` alone does not return 413 when the upstream doesn't read the body. An extra `Content-Length > 50000000` matcher returns a 413 `file_too_large` problem.
  - **Caddy:**
    - Runs with `cap_add: NET_BIND_SERVICE`; the binary has that file capability, so exec fails with `cap_drop: ALL` otherwise.
    - Access log drops URI, headers and TLS fields (ADR-033).
    - Site addresses and TLS come from `APP_SITE_ADDRESSES` / `APP_TLS`. A provided cert/key is mounted read-only from `/etc/foundry/tls`, not as a Compose secret, so `tls internal` needs no dummy secret files.
  - **`edge` network** (caddy only) has IP masquerade disabled. `verify-egress.sh` also probes caddy. On Docker Desktop caddy still has egress (Desktop's NAT ignores the option), so this must be confirmed on the Linux VM.
  - **Postgres logging is content-free:** `log_min_error_statement=panic`, `log_error_verbosity=terse`, parameter logging 0.
  - **Valkey:** no persistence, runs as uid 999 (avoids the entrypoint chown), **no auth yet**. Adding auth needs a new secret and a settings change.
  - **Placeholder SPA:** until Story 1.10 adds `frontend/index.html`, the caddy image ships a one-line placeholder page. `deploy/caddy/Dockerfile.dockerignore` limits the root build context to `frontend/` and the Caddyfile.
  - **Hardening:** all services use `pull_policy: never`, `read_only` (except postgres), `cap_drop: ALL`, `no-new-privileges` and the local log driver with rotation.
- **Known gaps / follow-ups:** a TLS key as a proper secret; Valkey auth; confirm egress blocking for caddy on the Linux VM; `alembic` CLI errors print tracebacks to the migrate container log (schema DDL only, no content).
- **Files created:** as in Owned File/Module Scope, plus `backend/docker-entrypoint.sh`, `deploy/postgres/pg_hba.conf` and `deploy/caddy/Dockerfile.dockerignore`.
