# 10.2: Operation catalogue and engine

**Story ID:** 10.2
**Epic:** 10 — Excel Processing
**Slug:** operation-catalogue-and-engine
**Status:** ready-for-dev

## Story

As a **banker**,
I want **plain-English workbook requests to become a fixed set of typed, validated operations run in a bounded process**,
so that **results are exact and repeatable, and no code from the model or the file is ever executed**.

## Acceptance Criteria

1. **Catalogue (`sheets/operations.py`):** a Pydantic discriminated union on `op`, one class per FR-050 operation, with bounded fields:
   `select_columns`, `rename_columns`, `filter_rows` (comparison, in-list, contains, date range, null checks; nested AND/OR, depth ≤ 3), `sort`, `deduplicate`, `fill_blanks` (value | forward), `cast_type`, `split_column`, `merge_columns`, `group_aggregate` (sum, mean, min, max, count, count_distinct, median), `pivot`, `unpivot`, `join` (inner | left on keys), `append`, `add_calculated_column` (10.3 grammar), `top_n`, and the column-wise finance ops `growth`, `cagr`, `margin`, `ratio`. A pipeline is `OperationPlan(input, steps: list[Operation] ≤ 20)`. Each class also renders a one-line plain-English description (`describe()`) for the plan card.
2. **Schema + validation (`sheets/schema.py`, `sheets/validate.py`):** `SheetSchema(columns: [(name, ColumnType)], row_count)` is the engine's view of a profile (10.1 produces it). `validate(plan, schemas)` walks the steps, threading the derived schema, and returns all errors with step index and a stable code: `column_not_found`, `type_mismatch`, `duplicate_column`, `too_many_columns` (pivot > 1,000), `expression_error` (10.3's codes), `unsupported`. No data is touched.
3. **Compilation (`sheets/engine.py`):** a validated plan compiles to a Polars `LazyFrame` pipeline (no `eval`, no Python UDFs, no `map_elements`). The result carries the output frame, its `SheetSchema`, and an operations log (`step, op, parameters, columns_used`). Finance ops compute in `Decimal` and agree with `sheets.calc` on the same inputs.
4. **Bounded execution (`sheets/pool.py`):** `run_plan(plan, frames, mode)` runs in a `ProcessPoolExecutor` child with `setrlimit` CPU ≤ 30 s and address space ≤ 2 GB, a 45 s wall-clock timeout, and output ≤ 5M cells. `mode="preview"` samples ≤ 1,000 input rows and returns the first 20 output rows; `mode="full"` runs everything. A breach kills the child, rebuilds the pool, and raises `OperationLimitError(code: cpu_limit | memory_limit | timeout | too_many_cells)` with a plain message. Frames go in and out as Arrow IPC bytes; the child does no file, DB or network I/O.
5. **Performance:** a 100k-row × 20-column frame through a 5-step plan (filter, group_aggregate, add_calculated_column, sort, top_n) completes in ≤ 10 s on the dev machine (`@pytest.mark.perf`).

## Dev Notes

- **ADR-030:** sheets are Polars DataFrames persisted as encrypted Parquet; operations are a Pydantic discriminated union validated against the profile (columns exist, types compatible, pivot ≤ 1,000 columns); calculated columns use the safe grammar, never `eval`; execution in a `ProcessPoolExecutor` with per-task `setrlimit` (CPU ≤ 30 s, AS ≤ 2 GB, output ≤ 5M cells, wall 45 s); previews on ≤ 1,000 sampled rows in api, full applies in the worker. [Source: architecture.md#adr-030-typed-spreadsheet-operation-engine-and-file-safety]
- **Catalogue v1** exactly as the addendum lists it. [Source: addendum.md#fr-050-operation-catalogue-v1]
- **FR-050:** plan in plain language + preview of the first 20 rows before applying; requests outside the catalogue are declined with the closest alternative (the agent does that; this story returns `unsupported`). [Source: prd.md#fr-050-transform-workbooks-with-typed-operations--must]
- **NFR-025:** every operation bounded (≤ 30 s CPU, ≤ 2 GB, ≤ 5M output cells); malformed input never affects other users. **NFR-024:** 100k rows ≤ 10 s. [Source: prd.md#nfr-025-spreadsheet-and-file-safety--must-security] [Source: prd.md#nfr-024-processing-performance--should-performance]
- **Not here:** sheet storage/profiles (10.1), tools (10.5), `operation_previews` table and apply job (10.6), XLSX writing (10.6). This story is pure engine and has no migration. [Source: epics.md#epic-10-excel-processing]
- **RLIMIT_CPU is cumulative per process:** set the soft limit to "CPU used so far + 30 s" at the start of each task (or use `max_tasks_per_child=1`), and set the address-space limit in the pool initializer. Use the `spawn` start method. [Inference]
- **Module rules:** `sheets` imports no fastapi; it may import `guardrails.grounding` types (10.4 does). [Source: backend/.importlinter]

## Testing

- **Approach:** unit tests per operation against hand-computed expected frames; validation tables; pool tests with hostile plans; one perf test.
- **Per-AC verification:**
  - AC #1 → every op parses from JSON and round-trips; unknown `op` rejected; > 20 steps rejected; `describe()` snapshots.
  - AC #2 → each error code produced with the right step index; schema threading (rename then filter on the new name passes).
  - AC #3 → reference outputs per op (incl. nulls, dates, mixed case strings); finance ops equal `calc.calculate` results to the last digit; a static check that `engine.py` contains no `map_elements`/`apply`/`eval`.
  - AC #4 → a cross join exploding past 5M cells → `too_many_cells`; a pathological plan hitting CPU → `cpu_limit`; a sleep-like long plan → `timeout`; the pool works for the next call afterwards; preview returns ≤ 20 rows from ≤ 1,000 sampled.
  - AC #5 → perf marker.
- **Fixtures:** small synthetic frames (financials by segment and year, customers with duplicates), plus the 1.7 synthetic workbooks loaded via openpyxl `data_only=True` into Polars.
- **Edge cases:** empty frame; column names with spaces and unicode; pivot exactly 1,000 columns (ok) vs 1,001 (error); `join` key type mismatch.

## Learnings from Previous Stories

- **10.3:** map profile types onto `ColumnType` (`number`, `integer`, `text`, `boolean`, `date`); pass the frame's real column names as the schema; `compile_expression(...).columns_used` feeds the operations log.
- **10.3:** integer overflow isn't checked; cast integers to float (or Decimal) before multiplying large columns.
- **10.4:** results use `Decimal`, formulas use U+2212 for minus, and `CalcError` messages are plain and safe to show.
- **2.4 follow-up:** a 10.3 timing test was flaky on a loaded machine; give perf assertions slack or mark them `perf`.
