# 10.3: Safe expression grammar

**Story ID:** 10.3
**Epic:** 10 — Excel Processing
**Slug:** safe-expression-grammar
**Status:** ready-for-dev

## Story

As the **builder**,
I want **calculated columns written in a small, closed expression language compiled to Polars**,
so that **"add a margin column" works without ever evaluating user- or model-supplied code**.

## Acceptance Criteria

1. **Grammar** (Lark, in `sheets/expressions.lark`):
   - number, string and boolean literals;
   - column references, `[Column Name]` or a bare identifier;
   - `+ - * /` and unary `-`; comparisons `= <> < <= > >=`; `AND OR NOT`; parentheses;
   - the functions `IF(c, a, b)`, `ROUND(x[, n])`, `ABS(x)`, `MIN(a, b, …)`, `MAX(a, b, …)`.

   Keywords and functions are case-insensitive. **Nothing else parses.**
2. **Compilation:** `compile_expression(text, schema: Mapping[str, ColumnType]) -> CompiledExpression(expr: pl.Expr, dtype, columns_used)`.
   - It checks that every column exists and that the types are compatible (numeric operators on numbers, comparisons between like types, an `IF` condition is boolean).
   - It infers the result type.
3. **Errors:** `ExpressionError(code, message, position)`, with codes:
   - `syntax`, `unknown_column`, `unknown_function`, `type_mismatch`;
   - `too_long` (> 1,000 chars), `too_deep` (> 32 levels), `too_complex` (> 500 nodes).

   Messages are plain English and name the column or function, never other data.
4. **Semantics:**
   - Division by zero gives **null** (never inf).
   - Null propagates through arithmetic.
   - `ROUND` uses half-away-from-zero, to match Excel.
   - Integer division yields a float.
   - Results equal a reference evaluator on ≥ 50 cases, including edge rows.
5. **Safety:** no `eval`, `exec`, `compile()` or attribute access anywhere. Python dunder names, lambdas, imports, subscripts and attribute chains are syntax errors. A fuzz test of 10,000 random inputs never raises anything but `ExpressionError` and never takes longer than 50 ms per input.

## Testing

- **Approach:** table-driven unit tests (expression, schema, input rows → expected output column), a reference evaluator, and fuzzing (Hypothesis optional; a seeded random generator is fine).
- **Per-AC verification:**
  - AC #1 → each construct parses; ≥ 20 rejected constructs (attribute access, `__class__`, lambda, `import`, `;`, backticks, `[a][b]` subscripts).
  - AC #2 → type checks: `[Revenue] / [Region]` → `type_mismatch`; unknown column named.
  - AC #3 → each error code with its position.
  - AC #4 → null and divide-by-zero rows; `ROUND(2.5)` = 3, `ROUND(-2.5)` = -3; ≥ 50 reference cases.
  - AC #5 → fuzz: 10k inputs, only `ExpressionError`, each ≤ 50 ms.
- **Edge cases:** column names with spaces, brackets and Unicode; very long numeric literals; empty expression; deeply nested parentheses.
