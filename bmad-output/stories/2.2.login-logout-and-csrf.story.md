# 2.2: Login, logout and CSRF

**Story ID:** 2.2
**Epic:** 2 — Authentication, Roles & Administration
**Slug:** login-logout-and-csrf
**Status:** ready-for-dev

## Story

As a **user**,
I want **to sign in and out securely, with my session protected from theft and forgery**,
so that **only I can act as me, and a stolen password alone isn't enough to keep going after a lockout**.

## Acceptance Criteria

1. **Login:** `POST /api/v1/auth/login` with `{username, password}`.
   - On success, it creates a session (`secrets.token_urlsafe(32)`; only `sha256(token)` is stored) and sets two cookies:
     - `__Host-session`: `HttpOnly; Secure; SameSite=Strict; Path=/`
     - `__Host-csrf`: random, JS-readable, `Secure; SameSite=Strict; Path=/`
   - It returns the `/auth/me` body. Any session cookie already on the request is revoked (session rotation).
   - On success it also rehashes a weak hash (`verify_and_rehash`), resets the failure counter and stamps `last_login_at`.
   - **Any failure** returns the same `401 invalid_credentials` problem in the same time: unknown user, wrong password, locked, deactivated or invited. Unknown users are hashed with `passwords.verify_dummy`.
2. **Lockout and limits:**
   - 5 consecutive failures lock the account for 15 minutes (`locked_until`). Even the correct password fails while the lock lasts.
   - The lock is audited, and a success after expiry resets the counter.
   - Login is rate-limited to **10 per minute per client IP** in Valkey; the 11th returns `429 rate_limited` with `Retry-After`.
3. **Session checks:** `app.auth.deps.current_user` reads `__Host-session` and looks the session up in Postgres **on every request**.
   - It rejects a session that is revoked, past its 12 h absolute expiry, or idle for more than 60 min.
   - The user must be `active`.
   - It updates `last_seen_at` at most once per `session_touch_interval_s`.
   - Failure returns `401 not_authenticated`.
   - `require_role(*roles)` returns `403 forbidden` for other roles and records `auth.access_denied`.
   - `GET /api/v1/auth/me` returns `{id, username, role}` (the frontend `CurrentUser` shape).
4. **CSRF:** a pure-ASGI middleware covers every state-changing request (`POST/PUT/PATCH/DELETE`) under `/api/v1`.
   - The `X-CSRF-Token` header must equal the `__Host-csrf` cookie (constant-time compare).
   - `Origin` must be one of the configured site origins, or `Sec-Fetch-Site` must be `same-origin`.
   - A failure returns `403 csrf_failed`.
   - Login and set-password (pre-session) are exempt from the token check but still get the Origin / Sec-Fetch-Site check.
5. **Logout:** `POST /api/v1/auth/logout` sets `revoked_at`, expires both cookies (`Max-Age=0`) and returns `204`. Any later request with that cookie returns `401`.
6. **Audit (metadata only):** in `app/auth/audit_events.py`:
   - `auth.login_succeeded`
   - `auth.login_failed`, with a reason enum and, for unknown users, `username_hash: KeyedHash`
   - `auth.account_locked`
   - `auth.logged_out`
   - `auth.access_denied`

   `assert_no_content` passes on every payload. No password, token or username ever appears in logs, audit rows or error bodies.
7. **Startup wiring:**
   - The API lifespan calls `auth.policy.preload()`, `crypto.kek.register_checks()` and `llm.readiness.register_checks()`.
   - The worker calls the two `register_checks()`.
   - A missing breached-password list fails API start-up.

## Dev Notes

- **Sessions:**
  - Opaque 256-bit tokens, with `sha256` in `sessions`. Idle timeout 60 min, absolute 12 h.
  - `last_seen_at` is updated at most once a minute, and every request looks the session up in Postgres, so revocation is immediate.
  - No JWTs, and no auth state in localStorage.

  [Source: architecture.md#ADR-006]
- **Cookies:** `__Host-session` (`HttpOnly; Secure; SameSite=Strict; Path=/`) and a JS-readable `__Host-csrf`. Every state-changing request sends `X-CSRF-Token`, with an `Origin`/`Sec-Fetch-Site` check for defence in depth. [Source: architecture.md#ADR-006]
- **Login protection:**
  - 5 failures → 15 min lock; generic responses; timing equalised with a dummy hash.
  - Session IDs rotate on login.

  [Source: architecture.md#ADR-006] [Source: prd.md#FR-002]
- Limits: login 10/min/IP. [Source: architecture.md#6-api-specifications]
- NFR-007: OWASP ASVS L2 for authentication and sessions; revocation ≤ 5 s; credentials not accessible to scripts. [Source: prd.md#NFR-007]
- **LOCKED:** all auth goes through `auth.deps.current_user` / `require_role`. [Source: architecture.md#ADR-006]
- The frontend client (1.10) already reads `__Host-csrf`, sends `X-CSRF-Token` and redirects to `/login` on 401. `CurrentUser` is `{id, username, role}`. [Source: frontend/src/api/client.ts] [Source: frontend/src/auth/RequireAuth.tsx]
- Errors use `core.errors.ProblemException` (RFC 9457). Audit through `audit.writer.record(..., session=tx)` so each event commits with its action. [Source: architecture.md#ADR-003] [Source: architecture.md#ADR-032]
- The client IP comes from `X-Forwarded-For` as set by Caddy (uvicorn runs with `--proxy-headers`). Rate-limit keys use the IP, never the username. [Inference]
- Q8 (are the session timeouts acceptable?) is open. Keep the values in `AuthSettings` (2.1). [Source: addendum.md#open-questions]

## Testing

- **Approach:** API tests with `app_client` + `pg` + `valkey`; unit tests for the CSRF middleware and cookie attributes.
- **Per-AC verification:**
  - AC #1 → success sets both cookies with the exact attributes; the four failure kinds return byte-identical bodies; the median timing of unknown vs wrong password is within 30%; a pre-existing session cookie is revoked.
  - AC #2 → the 5th failure locks; the right password fails during the lock and succeeds after (fake clock); the 11th login in a minute → 429.
  - AC #3 → revoked, absolute-expired, idle-expired and deactivated each → 401; touch throttling (no write within 60 s); `require_role` → 403 + audit row.
  - AC #4 → missing or mismatched token → 403; cross-site Origin → 403; GET is unaffected.
  - AC #5 → logout then reuse → 401; cookies expired.
  - AC #6 → `assert_no_content` on every auth event; captured logs and responses contain no planted password or token.
  - AC #7 → a missing breached list fails app start; `/readyz` lists `kek_loaded` when the KEK is absent.
- **Edge cases:** Unicode usernames (citext + NFKC); a 1 MB password body (`too_long` handled before hashing); concurrent logins; a clock change during the lock.

## Learnings from Previous Stories

- **2.1 repository:**
  - `repository.*` takes the caller's `AsyncSession`. `increment_failed_logins` returns the new count; `record_successful_login` resets the lock.
  - `passwords.verify_and_rehash` and `verify_dummy` exist; `AuthSettings` holds the TTLs and the touch interval.
- `transaction()` cannot be nested. Pass `session=tx` to `audit.writer.record` so the event joins the action's transaction. (from 7.1)
- Readiness check functions exist but nothing calls them yet: `llm.readiness.register_checks`, `crypto.kek.register_checks`. (from 1.5, 8.1)
- Valkey URL setting: `APP_VALKEY_URL` (shared alias in `JobsSettings`). (from 1.11)
- `audit.registry.discover()` imports only `app/<module>/audit_events.py`, and `python -m app.audit.check_models` relies on it. Event models in other files would escape the CI check. (from 7.1)
