# 2.4: Change own password

**Story ID:** 2.4
**Epic:** 2 — Authentication, Roles & Administration
**Slug:** change-own-password
**Status:** ready-for-dev

## Story

As a **user**,
I want **to change my password while signed in**,
so that **I can rotate it myself, and any other device using my account is signed out**.

## Acceptance Criteria

1. `POST /api/v1/auth/change-password` `{current_password, new_password}` (authenticated, CSRF-protected) verifies the current password.
   - A wrong current password → `400 current_password_invalid`, and it **counts toward the lockout** (5 → 15 min) like a failed login.
2. The new password goes through the 2.1 policy (length, breached list, username) → `422 password_rejected` with reason codes. Reusing the current password → `422 password_unchanged`.
3. In one transaction it:
   - sets the new Argon2id hash;
   - **revokes every other session** of the user, keeping the current one;
   - records `auth.password_changed` with a revoked-session count.

   Returns `204`.
4. No password value appears in logs, audit rows or error bodies. Responses don't reveal which policy check failed beyond the reason codes.

### Verification

- `make lint`, `make typecheck` and `make test` all exit 0: backend **1353 passed, 6 skipped** (12 new in `tests/auth/test_change_password.py`), frontend 94 passed.
- **AC #1:** five wrong current passwords give 400 `current_password_invalid` and raise `failed_login_count` 1→5. Then the account is locked: the right current password and a fresh login both fail. The failures share one counter with failed logins (3 login failures + 1 change failure = 4). `auth.password_change_failed` carries the count (`null` while locked); `auth.account_locked` is recorded at 5.
- **AC #2:** `too_short`, `too_short`+`breached`, `contains_username` and `too_long` come back as 422 `password_rejected` with those `reasons`. The same password, and an NFKC-equivalent one (fullwidth letters), give 422 `password_unchanged`.
- **AC #3:** 204; the current session still works and the other session gets 401; the old password no longer signs in and the new one does. `auth.password_changed` has `sessions_revoked: 1`. Two concurrent changes from one session: one 204, one 400 (the second is checked against the first's new password).
- **AC #4:** planted current and new passwords appear in no response, log line or audit row; every payload passes `assert_no_content`. Without a CSRF token the request is refused 403 `csrf_failed`; with a valid CSRF pair but no session it's 401.

### Decisions

- **Order:** current password first (so a wrong one always counts), then the policy, then "unchanged". "Unchanged" is a hash verification of the new password against the stored hash: it uses the same NFKC normalisation as hashing, so equivalent forms count as the same password.
- **Lockout:** the same counter, threshold (`login_max_failures`) and lock (`lockout_s`) as logins, including "an expired lock starts a new run". While locked, the check fails without verifying or counting. The failure is committed (the function returns an outcome rather than raising inside the transaction), so the 400 can't roll it back.
- **Separate failure event** `auth.password_change_failed` rather than reusing `auth.login_failed`, so compliance can tell the two apart; the lock itself reuses `auth.account_locked`.
- **Concurrency:** the user row is locked `FOR UPDATE` for the whole check.
- A successful change clears the failure counter, as a successful login does.
