# 3.1: Conversations schema and API

**Story ID:** 3.1
**Epic:** 3 — Chat Experience
**Slug:** conversations-schema-and-api
**Status:** ready-for-dev

## Story

As a **user**,
I want **my conversations stored encrypted, private to me, and bound to one space and a selected document set**,
so that **I can come back to my work, and nobody else, not even a workspace colleague, can read it**.

## Acceptance Criteria

1. **Migration `3_1_conversations`** creates the tables below, each with `space_id NOT NULL` + RLS via `spaces.rls.enable_space_rls`:
   - `conversations` (`space_id`, `owner_user_id`, `title_enc`, `summary_enc`, `summary_upto_message_id`, `expires_at`, `deleted_at`, timestamps)
   - `conversation_documents` (PK `conversation_id, document_id`)
   - `messages` (`conversation_id`, `space_id`, `role`, `content_enc`, `status`, `decline_category`, `model_name`, `prompt_version`, `correlation_id`, `latency_ms`, `token_usage`)
   - `message_tables` (`message_id`, `space_id`, `title_enc`, `columns_enc`, `rows_enc`, `source_locators` jsonb)
   - `message_sources` (`message_id`, `space_id`, `kind`, `document_id`, `locator`)

   Conversations and their children are **owner-only even inside a workspace** (`owner_column`).
2. **Encryption:** each conversation gets an object key (`conversation`). Titles, message content and table cells are `*_enc` via `crypto.fields`, with per-field AAD. No plaintext content column exists.
3. **API:**
   - `GET /api/v1/conversations` (own; title, date, space; newest first; cursor-paginated).
   - `POST /api/v1/conversations` `{space_id}` (caller must be a member).
   - `GET` / `PATCH` (rename) / `DELETE /api/v1/conversations/{id}`. Delete is permanent: it shreds the conversation key and deletes the rows.
   - Not accessible → 404.
4. **Selected set:** `PUT /api/v1/conversations/{id}/documents` `{document_ids}` replaces the set.
   - Every document must be in the conversation's space and `ready`, checked through a `chat.selected_set.DocumentResolver` that 9.1 registers.
   - **Until a resolver is registered, only an empty set is accepted** (non-empty → `422 document_not_found`).
   - `GET` on the conversation returns the set.
5. **Repository for 3.2:** `chat.repository` functions take `AccessContext` and the session:
   - `append_message`, `update_message` (status / content), `list_messages` (decrypted), `add_message_table`, `add_message_sources`;
   - `set_summary` (for context condensation).

   Audit: `chat.conversation_created`, `chat.conversation_deleted` (IDs only).

## Dev Notes

- **Data model:** `conversations`, `conversation_documents` (same `space_id` enforced), `messages`, `message_tables`, `message_sources` as specified. [Source: architecture.md#5-data-model]
- **Space binding:** conversations carry `owner_user_id` so they stay private to their creator even inside a workspace, and a conversation is bound to one space whose documents form its selected set. [Source: architecture.md#ADR-023]
- **FR-055:** the conversation works only on the selected set; documents from a workspace can be selected only by its members. [Source: prd.md#FR-055]
- **FR-008:** the list shows title and date; a user sees only their own; deletion is permanent and conversations expire under the 30-day rule. [Source: prd.md#FR-008] [Source: prd.md#FR-052]
- **Paths:** `GET/POST /conversations`, `GET/PATCH/DELETE /conversations/{id}`, `PUT /conversations/{id}/documents`. The SSE `POST .../messages` is 3.2. [Source: architecture.md#6-api-specifications]
- Messages, titles and message tables are among the encrypted fields. [Source: architecture.md#ADR-028]
- **Why no documents yet:** `documents` arrives in 9.1 (wave 6), so this story adds no FK from `conversation_documents.document_id`; 9.1 adds it with its resolver. [Inference]
- **Migration heads:** this story's migration and 7.2's both revise `8_2_spaces` (wave 5). Whichever merges second adds an `alembic merge` revision joining the two heads, and owns that file. [Source: epics.md#shared-file-conventions-parallel-safety-rules-for-every-story]

## Testing

- **Approach:** API + repository tests with `pg`, users A and B sharing a workspace, and an outsider.
- **Per-AC verification:**
  - AC #1 → B (same workspace) sees 0 of A's conversations and messages via the API **and** via raw SQL under B's RLS context; no context → 0 rows.
  - AC #2 → a raw DB scan finds no planted title or message text.
  - AC #3 → list ordering and pagination; another user's ID → 404; delete → `KeyDestroyed` on old ciphertext.
  - AC #4 → a non-empty set without a resolver → 422; with a test resolver, a wrong-space document → 422.
  - AC #5 → round-trip messages, tables and sources; `assert_no_content` on audit rows.
- **Edge cases:** a conversation in a workspace the owner was then removed from (404, not 403); a closed space; long titles.

## Learnings from Previous Stories

- **8.2:**
  - `enable_space_rls(op, table, owner_column="owner_user_id")` gives owner-only policies.
  - `AccessContext.rls_settings()` goes to `transaction(context=...)`.
- **Encryption (8.1):**
  - `create_object_key(tx, space_id, "conversation", id)` → `KeyRef`; `encrypt_field(ref, "title", text)`.
  - Key lookups work before commit (the cache is populated on create).
- **Shredding (8.1):** `shred_object(tx, "conversation", id)`; ciphertext becomes unrecoverable at once in this process.
