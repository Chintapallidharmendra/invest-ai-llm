# 3.2: Turn orchestrator and SSE

**Story ID:** 3.2
**Epic:** 3 — Chat Experience
**Slug:** turn-orchestrator-and-sse
**Status:** ready-for-dev

## Story

As a **banker**,
I want **my question answered as a live stream that passes every safety stage in a fixed order, and that I can stop**,
so that **answers start fast, nothing unsafe reaches me, and every turn is stored privately**.

## Acceptance Criteria

1. **Contracts (this story owns them; 3.3 and Epic 4 implement them):**
   - `app/guardrails/pipeline.py`: `TurnInput` (user ID, space ID, conversation ID, raw text, selected document IDs, correlation ID), `InputDecision` (`Pass(annotations)` | `Block(code, status, detail, extensions)` | `Decline(category, text)`; `Pass.annotations` are short enum-like strings such as `scope_category`, merged into `TurnRequest.annotations`), `InputStage` protocol (`slot` 0–3, `name`, `async check(turn)`), `OutputGate` protocol (`open(turn) → session` with `add_grounding(sources)`, `async feed(text) → [GateEvent]`, `async finish() → [GateEvent]`, `GateEvent` = `Delta(text)` | `Replace(text, reason_code)`), `FinalModeration` protocol (`async check(turn, text) → Verdict(safe, category)`), a registry (`register_input_stage`, `register_output_gate`, `register_final_moderation`) and `discover()` that imports every `app/guardrails/stage_*.py`.
   - `app/assistant/contract.py`: `TurnRequest` (AccessContext, conversation/space IDs, user text, selected document IDs, decrypted history, rolling summary + `summary_upto_message_id`, `annotations` from input stages, correlation ID), `TableResult`, the `AgentEvent` union (`Status`, `TextChunk`, `Table`, `Sources`, `Plan`, `Job`, `Grounding`, `SummaryUpdate`, `AgentDone`) and the `AgentRunner` protocol (`run(req) → AsyncIterator[AgentEvent]`). The runner is loaded from `app.assistant.runner` when that module exists.
2. **`POST /api/v1/conversations/{id}/messages`** `{text}` (1–4,000 chars; role `user`; CSRF) runs, in order, **before any write or stream**: load the conversation (404) → slots 0, 1, 2, 3 → **stage 4 access check** (conversation space still accessible; selected set re-checked through `selected_set.check`; failure → 404 / 409 `not_ready`).
   - `Block` → that HTTP problem (e.g. 422 `pii_detected`, 429 `rate_limited`); **the text is not persisted or logged**.
   - Any stage exception or timeout → 503 `safety_unavailable` (fail closed).
   - A missing slot (0, 1, 2, 3, output gate, final moderation) or a missing runner → 503 `safety_unavailable` / `assistant_unavailable`, unless `APP_CHAT_ALLOW_MISSING_STAGES=true` (tests and local dev only; default false). `/readyz` registers a `chat_pipeline` check that fails while any slot is missing and the flag is false.
   - A second turn while one is in flight on the same conversation → 409 `turn_in_progress` (Valkey lock with TTL).
3. **Stream** (`text/event-stream`), events per ADR-003/025 as Pydantic models:
   - persist the user message and a `pending` assistant message, then `meta {conversation_id, user_message_id, assistant_message_id}`;
   - `Decline` from slot 2/3 → `delta` with the template text and `done {finish_reason: "declined"}`; the assistant message is stored `declined` with `decline_category`;
   - otherwise run the agent: `Status` → `status`; `Table` → `table` (and `add_message_table`); `Plan` → `plan`; `Job` → `job`; `Grounding` → `gate.add_grounding`; **every `TextChunk` goes through the output gate**, which alone produces `delta` / `replace`;
   - at the end: `gate.finish()`, then final moderation on the full visible text (unsafe → `replace` with the withheld template, `finish_reason: "withheld"`), then `sources`, persist the assistant message (content, status, model, prompt version, latency, token usage), tables and sources, `SummaryUpdate` → `set_summary`, then `done {finish_reason, latency_ms}`.
   - An exception after the stream has started → `error {problem}` and status `failed`.
4. **Cancellation:** when the client disconnects, the agent run is cancelled (the LLM stream closes), the text delivered so far is stored with status `cancelled`, the lock is released, and no further events are sent.
5. **History and SSE schemas:** `GET /api/v1/conversations/{id}/messages` (owner only; oldest first; cursor; decrypted content, status, `decline_category`, tables and sources as `list_messages` returns them) lets the chat UI reload a conversation. **SSE schemas in OpenAPI:** `GET /api/v1/chat/event-schemas` (role `user`) returns an example list typed as the union of all event models, so `openapi-typescript` generates them. `chat/routes.py` mounts every `app/chat/routes_*.py` router (like `spaces`).
6. **Audit and observability:** `chat.turn_completed` (IDs, `finish_reason`, latency, per-stage ms, token counts), `chat.turn_blocked` (slot, code). No message text, decline text, or model output in audit, logs or spans.

## Dev Notes

- **Stage order (LOCKED):** 0 auth/CSRF/rate limit → 1 identifier gate → 2 guard moderation → 3 scope router → 4 access check → 5 agent → 6 output gate → 7 final moderation. Stage 1 runs on raw input before any write. Any error or timeout in 1–4, 6, 7 means refusal (503 `safety_unavailable`, or `replace` + `withheld`). [Source: architecture.md#adr-024-guardrail-pipeline-v2-supersedes-adr-010]
- **Input-stage blocks are HTTP problems before the stream starts, never SSE events.** [Source: architecture.md#adr-003-response-error-and-sse-event-conventions]
- **Event set:** `meta`, `status {stage, label}`, `delta {text}`, `table {table_id, title, columns, rows, source, as_of, notes}`, `sources {items: [{kind, document_id, locator}]}`, `replace {text, reason_code}`, `plan {preview_id, steps, preview}`, `job {job_id, kind, status}`, `done {finish_reason: stop|declined|cancelled|withheld, latency_ms}`, `error {problem}`. [Source: architecture.md#adr-003-response-error-and-sse-event-conventions] [Source: architecture.md#adr-025-output-gating-grounding-and-rendering-v2-supersedes-adr-011]
- **No token reaches the client except through the output gate;** tables come from tool results (`TableResult`), never model text. [Source: architecture.md#adr-025-output-gating-grounding-and-rendering-v2-supersedes-adr-011]
- **Turn sequence:** stages 0–4 → persist the user message (encrypted) → `meta`, `status` → agent with tools → gate → `delta` → final moderation → `sources` → persist the assistant message → audit → `done`. [Source: architecture.md#turn-sequence-document-qa]
- **Streaming only here;** cancel = client aborts the request; the server detects the disconnect and cancels generation. [Source: architecture.md#adr-002-restjson-under-apiv1--sse-for-chat-streaming]
- **FR-006:** status indicator, stop, plain failure message with retry. FR-055: answers only from the selected set. [Source: prd.md#fr-006-streamed-answers--must] [Source: prd.md#fr-055-choose-which-documents-a-conversation-uses--must]
- **Why the contracts live in `guardrails` and `assistant`:** `.importlinter` forbids domain modules (guardrails, assistant, documents…) from importing `app.chat`. Chat imports them; never the reverse. [Source: backend/.importlinter]
- **Why missing slots fail closed:** guard stages arrive in wave 7 (4.2, 4.3, 4.5). Until then, the deployed app refuses turns rather than answering unguarded (NFR-013). [Source: prd.md#nfr-013-fail-safe-degradation--must-reliability] [Inference]
- **Withheld turns:** `message_status` has no `withheld`; store `declined` with `decline_category = "output_withheld"`. [Inference, from 3.1 enum]
- **Context and prompts are 3.3's** (`context.build`, rolling summary). The orchestrator passes history and summary in and persists the `SummaryUpdate` it gets back, because `assistant` cannot import `chat`. [Source: architecture.md#adr-015-conversation-context-management-within-8k-tokens]
- **NFR-003:** stages 1–2 ≤ 500 ms; record per-stage timings (metadata) for 7.10. [Source: prd.md#nfr-003-guardrail-overhead--must-performance]

## Testing

- **Approach:** API tests with `httpx.AsyncClient` streaming, fake stages registered per test, a scripted fake `AgentRunner`, `pg` and fake Valkey; one integration test with the 1.6 fake LLM behind a trivial runner.
- **Per-AC verification:**
  - AC #1 → registry rejects a duplicate slot; `discover()` imports a test `stage_*` module; `missing()` lists unfilled slots.
  - AC #2 → stage order recorded by fakes; a `Block` at slot 1 → 422 and **no** message rows and no text in captured logs; a raising stage → 503; missing slot with flag false → 503 and `/readyz` failing; concurrent turn → 409; selected `pending` document → 409 `not_ready`.
  - AC #3 → event sequence for a normal turn; decline path; a fake gate that replaces a chunk produces `replace`; unsafe final moderation → `withheld`; persisted rows decrypt to the visible text; tables and sources stored.
  - AC #4 → abort mid-stream: runner's `aclose` called, message `cancelled`, lock released.
  - AC #5 → history endpoint returns the stored turn (tables, sources) to the owner and 404 to a workspace colleague; OpenAPI contains every event model; chat sub-routers mounted.
  - AC #6 → `assert_no_content` on audit rows; a canary in the user text is absent from logs and spans.
- **Edge cases:** empty selected set (concept-only turn still runs); conversation deleted mid-turn; runner raising before the first chunk; Valkey down for the lock (503).

## Learnings from Previous Stories

- **3.1:** `append_message(..., status=PENDING)`, then `update_message(...)`; `list_messages` returns decrypted history with tables and sources; `set_summary` for condensation. Repository queries filter `owner_user_id` as well as RLS.
- **1.5:** `Gateway.stream_chat` raises `LLMStreamInterrupted` when a stream breaks; discard partial text. Cancelling the async iterator closes the upstream stream.
- **1.10:** the frontend `api/sse.ts` already parses POST-based SSE with the event names above; keep them identical.
- **8.2:** use `build_access_context(user)` and re-read membership per request (no caching).
- **2.2:** CSRF and session checks come from `auth.deps`; streaming responses still pass through the correlation-ID middleware.
