# 3.6: Answer ratings

**Story ID:** 3.6
**Epic:** 3 — Chat Experience
**Slug:** answer-ratings
**Status:** ready-for-dev

## Story

As a **banker**,
I want **to rate an answer thumbs up or down with an optional comment**,
so that **the team learns what works, while my comment stays as confidential as the answer itself**.

## Acceptance Criteria

1. **Migration `3_6_feedback`** (revises `9_1_documents`) creates `feedback` (`message_id`, `space_id`, `owner_user_id`, `rating` `up|down`, `comment_enc` nullable, timestamps), unique on `message_id`, with a composite FK `(message_id, space_id, owner_user_id) → messages(id, space_id, owner_user_id) ON DELETE CASCADE` and **owner-only** RLS (`enable_space_rls(..., owner_column="owner_user_id")`).
2. **`PUT /api/v1/messages/{id}/feedback`** `{rating, comment?}` (comment ≤ 1,000 chars; role `user`; CSRF) creates or replaces the rating on the caller's own **assistant** message → 200 with `{message_id, rating, has_comment, updated_at}`. A user message, another user's message (even in the same workspace) or an unknown ID → 404. `DELETE` the same path removes it → 204.
3. **Encryption:** the comment is encrypted under the conversation's object key with field `feedback_<message hex>_comment`; no plaintext comment column exists. Deleting the conversation (3.1) removes feedback by cascade, and its ciphertext is unreadable after the key is shredded.
4. **`GET /api/v1/conversations/{id}/feedback`** (owner) → `{items: [{message_id, rating, has_comment}]}` so the chat UI can show existing ratings; the comment text is returned only by `GET /api/v1/messages/{id}/feedback`.
5. **Aggregates without content:** audit `chat.feedback_set` (IDs, `rating`, `has_comment`) and `chat.feedback_removed`. Admin-facing counts (FR-011, 7.9) are derived from these events; no admin endpoint reads `feedback`.

## Dev Notes

- **Data model:** `feedback(message_id, user_id, space_id, rating, comment_enc)`; this story names the owner column `owner_user_id` to match the other chat tables and the owner-only RLS helper. [Source: architecture.md#conversations--outputs] [Inference]
- **FR-011:** thumbs up/down + optional comment; the comment is encrypted like other content (NFR-021); only aggregate counts are visible to the admin. [Source: prd.md#fr-011-user-rates-an-answer--could]
- **Endpoint:** `PUT /api/v1/messages/{id}/feedback`. [Source: architecture.md#chat]
- **Encryption:** feedback comments are an encrypted field; AAD = space ‖ object ‖ field. [Source: architecture.md#adr-028-envelope-encryption-at-rest-with-per-object-keys-crypto-shredding]
- **Isolation:** conversations and children are owner-only even inside a workspace; not accessible → 404; admin endpoints never join content tables. [Source: architecture.md#adr-023-space-scoped-access-control-and-isolation-supersedes-adr-007]
- **Routing:** `chat/routes.py` mounts `routes_*.py` after 3.2, so this story adds `routes_feedback.py` without touching shared files. Audit events go in `audit_events_feedback.py` (discovered). [Source: story 3.2]
- **UI:** the thumbs buttons and comment box belong to the chat UI (3.4, wave 9), which calls these endpoints. [Inference]
- **Migration heads:** 9.4's `9_4_segments` also revises `9_1_documents` in wave 7. Whichever merges second adds the `alembic merge` revision and owns it. [Source: epics.md#shared-file-conventions-parallel-safety-rules-for-every-story]

## Testing

- **Approach:** API + repository tests with `pg`; users A and B in one workspace.
- **Per-AC verification:**
  - AC #1 → B sees 0 feedback rows for A's messages via raw SQL under B's context; no context → 0; FK rejects a mismatched owner.
  - AC #2 → create then replace (one row); rating on a user-role message → 404; B rating A's message → 404; delete → 204 then 404 on GET.
  - AC #3 → byte scan finds no planted comment; after conversation delete, no feedback rows and `KeyDestroyed` on the old ciphertext.
  - AC #4 → list returns ratings without comment text; GET single returns the decrypted comment to the owner only.
  - AC #5 → `assert_no_content` on audit rows; `has_comment` true/false correct.
- **Edge cases:** 1,001-char comment → 422; comment cleared by sending `null`; rating a `cancelled` or `declined` assistant message (allowed).

## Learnings from Previous Stories

- **3.1:** owner-only RLS needs the owner column on every child; composite FKs `(parent_id, space_id, owner_user_id)` keep them equal to the parent's. Per-row field names under the one conversation key: `message_<hex>_content` etc.
- **3.1:** repository queries also filter `owner_user_id = ctx.user_id` and check `ctx.can_access(space_id)`.
- **3.1:** only role `user` has conversations (`require_role(Role.USER)`).
- **alembic env** imports only `app/<module>/models.py`; import `models_feedback` from it.
