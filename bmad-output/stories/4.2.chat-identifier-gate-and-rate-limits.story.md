# 4.2: Chat identifier gate and rate limits

**Story ID:** 4.2
**Epic:** 4 — Guardrails & Data Protection
**Slug:** chat-identifier-gate-and-rate-limits
**Status:** ready-for-dev

## Story

As a **compliance-minded banker**,
I want **a chat message containing a PAN, Aadhaar, account or card number to be blocked before anything stores or sees it, and chat use to be rate-limited**,
so that **personal identifiers never reach the model, the database or the logs, and one user can't starve the others**.

## Acceptance Criteria

1. **Slot 0 — rate limit (`guardrails/stage_ratelimit.py`):** per user, ≤ 10 messages/min and ≤ 300/day (settings `APP_GUARDRAILS_CHAT_PER_MINUTE`, `APP_GUARDRAILS_CHAT_PER_DAY`). Over the limit → `Block(429, rate_limited, retry_after_s)`. Valkey unavailable → `Block(503, rate_limit_unavailable)`. Audit `guardrails.rate_limited` (window only).
2. **Slot 1 — identifier gate (`guardrails/stage_identifiers.py`):** runs `identifiers.detect()` on the raw message (high-risk types only, with the benign allow-list). Any finding → `Block(422, pii_detected, detected_types=[sorted unique types])`. The problem `detail` says which types were found and that the message was not sent or saved; it never contains the value or the message.
3. **Discarding:** on a block, the message text is not persisted, logged, traced, audited or sent to any model. Audit `guardrails.pii_blocked` carries only the types and a count per type.
4. **Bounded and fail closed:** detection runs off the event loop with a 1 s timeout; a timeout or engine error → the stage raises, so 3.2 returns 503 `safety_unavailable`. Messages are already ≤ 4,000 chars (3.2).
5. **Readiness and model staging:** importing the stage module calls `identifiers.get_engine()` lazily via a registered readiness check `identifiers` (fails if the spaCy model is missing). The spaCy `en_core_web_sm` 3.8.0 model is added to `deploy/models/manifest.yaml` (SHA-256 per 4.1) and the engine path defaults to `/models/spacy/en_core_web_sm`.
6. **Performance:** slot 1 on a 4,000-char message ≤ 150 ms p95 on the dev machine (`@pytest.mark.perf`), keeping stages 1–2 within the 500 ms budget.

## Testing

- **Approach:** stage unit tests with fake Valkey; one end-to-end turn through 3.2's endpoint with all other slots faked.
- **Per-AC verification:**
  - AC #1 → 11th message in a minute → 429 with `retry_after_s`; 301st in a day → 429; Valkey down → 503.
  - AC #2 → PAN, Aadhaar (contiguous, spaced, `XXXX XXXX 1234`), card (Luhn), UPI, account + "a/c" context → 422 with the right types; a company GSTIN, CIN and ISIN pass.
  - AC #3 → a canary PAN in a blocked message is absent from DB rows (byte scan), captured logs, spans and audit rows; no request reached the fake LLM.
  - AC #4 → a patched `detect` that sleeps 2 s → 503; one that raises → 503.
  - AC #5 → readiness fails with a missing model path, passes with the staged model.
  - AC #6 → perf marker.
- **Edge cases:** a message that is only an identifier; identifiers split by line breaks; non-ASCII digits.

## Learnings from Previous Stories

- **4.1:** call `identifiers.get_engine()` at start-up (readiness) so a missing model fails the boot; log only `*_count` fields. A blank pipeline (`spacy.blank("en").to_disk(...)`) works identically if the wheel is a problem.
- **4.1:** a proprietor's GSTIN embeds a personal PAN and is allow-listed like any GSTIN; bare 10-digit mobiles near "account"/"bank" are reported as `BANK_ACCOUNT`. Both stay as-is here; 4.7 records them.
- **2.2:** `auth.ratelimit.hit(scope, subject, limit=, window_s=)` hashes the subject; raises `RateLimitUnavailableError` when Valkey is down.
