# 8.1: Crypto key hierarchy

**Story ID:** 8.1
**Epic:** 8 — Workspaces, Isolation & Encryption
**Slug:** crypto-key-hierarchy
**Status:** ready-for-dev

## Story

As **compliance**,
I want **all deal content encrypted with per-object keys under per-space keys under a master key**,
so that **data at rest is protected and any document can be made unrecoverable by destroying its key**.

## Acceptance Criteria

1. **KEK:** `crypto.kek` loads the 256-bit KEK from the secret file (`/run/secrets/kek`, raw 32 bytes or base64), with `APP_CRYPTO_KEK_VERSION`. A missing or wrong-length KEK makes readiness fail with check name `kek_loaded`. The KEK is never logged, never written to the DB and never returned by any function.
2. **Key tables:** migration `8_1_keys` creates:
   - `space_keys(space_id uuid unique, wrapped_key bytea, kek_version int)`
   - `object_keys(object_type text, object_id uuid, space_id uuid, wrapped_key bytea, created_at)` with unique `(object_type, object_id)`

   **No FK to `spaces` yet**; Story 8.2 adds it. `app_rw` gets SELECT/INSERT/DELETE (no UPDATE except via rotation).
3. **Wrapping:**
   - `create_space_key(space_id)` makes a random 32-byte key wrapped with AES-256-GCM under the KEK (AAD = `space_id`);
   - `create_object_key(space_id, object_type, object_id)` makes a random key wrapped under the space key (AAD = `space_id||object_type||object_id`);
   - unwrap verifies the AAD.
4. **Field encryption:**
   - `encrypt_field(key_ref, field, plaintext: bytes|str) -> bytes` uses the format `version(1) | nonce(12) | ciphertext | tag(16)` with AAD = `space_id||object_id||field`;
   - `decrypt_field` raises `IntegrityError` on tamper or on an AAD mismatch, e.g. ciphertext moved to another object, space or field.
5. **File encryption:** `encrypt_stream` / `decrypt_stream` process 1 MiB chunks, each with its own nonce. AAD includes the object, the chunk index and a final-chunk flag, so **truncation, reordering and appending are detected**. Decrypt streams back for downloads without loading the whole file.
6. **Cache and shredding:**
   - unwrapped keys are cached in memory, TTL ≤ 5 min, size-bounded;
   - `shred_object(object_type, object_id)` and `shred_space(space_id)` (space key + all its object keys) delete key rows and evict cache entries;
   - after a shred, decrypt raises `KeyDestroyed`.
7. **Rotation:** `rotate_kek(new_kek)` re-wraps all space keys in one transaction and bumps `kek_version` (no data re-encryption). Only `app.crypto` imports `cryptography` (import-linter).

## Dev Notes

- **Envelope hierarchy:** KEK (host file, root-only, never in DB or backups, escrowed
  offline) → space key (wrapped by KEK) → object key per document, output and
  conversation (wrapped by the space key). AES-256-GCM with AAD
  `space_id || object_id || field`. Files in 1 MB chunks with per-chunk nonces. Key cache
  ≤ 5 min. Crypto-shredding by deleting key rows. KEK rotation re-wraps space keys.
  [Source: architecture.md#ADR-028]
- **Azure amendment:** no Key Vault; the KEK is a root-only file at `/etc/foundry/kek`
  (0400), mounted as a Compose secret, on the OS disk (excluded from backups). Disk-level
  encryption is Azure default SSE. App-level encryption is the primary control.
  [Source: architecture.md#ADR-028] (amendment) [Source: decision-log.md#2026-10-07--azure-uat-host-no-key-vault-default-azure-disk-encryption]
- Encrypted columns use the `_enc` suffix and store bytes from `encrypt_field`.
  [Source: architecture.md#ADR-004] (amendment)
- **Deletion:** shredding is step 2 of the delete pipeline (synchronous, seconds).
  Remaining ciphertext becomes unreadable once the 30-day backups that still hold the
  wrapped key roll over. [Source: architecture.md#ADR-035] [Source: prd.md#NFR-022]
- Readiness includes "KEK loaded"; a missing KEK makes the system refuse work (fail
  closed). [Source: architecture.md#ADR-033] [Source: prd.md#NFR-013]
- Only `crypto` imports `cryptography`; all content fields go through
  `encrypt_field`/`decrypt_field`. [Source: architecture.md#ADR-038] [Source: architecture.md#ADR-028]
- Nonces are 96-bit random per encryption. With one key per object, nonce-reuse risk is
  negligible at this volume. [Inference]
- Key tables hold wrapped keys only (no content), so no RLS here. Access goes through
  `crypto` APIs. 8.2 adds the FK. [Inference]

## Testing

- **Approach:** unit tests (format, AAD, tamper) + integration tests (key tables, shred, rotate) with the `pg` fixture.
- **Per-AC verification:**
  - AC #1 → missing or short KEK fails readiness; logs captured during startup contain no key bytes.
  - AC #2 → migration up/down; a duplicate object key is rejected.
  - AC #3 → unwrapping with the wrong `space_id` AAD fails.
  - AC #4 → a round trip works; flipping one byte fails; decrypting with another object's AAD fails; the same plaintext encrypts to different ciphertexts.
  - AC #5 → a 10 MB random file round-trips by streaming; removing the last chunk, swapping chunks 2 and 3, or appending a chunk fails.
  - AC #6 → after `shred_object`, decrypt raises `KeyDestroyed` even if the cache was warm; after `shred_space`, all objects in the space fail.
  - AC #7 → after rotation, old data still decrypts with the new KEK; the old KEK no longer unwraps.
- **Fixtures:** a test KEK via a tmp secret file; Hypothesis-style random payloads (optional).
- **Edge cases:** empty plaintext; > 2 GB stream (chunk counter width); concurrent `create_object_key` for the same object (unique constraint, return the existing key).

### Decisions

- **KEK formats:** besides raw 32 bytes and base64, 64 hex digits are accepted, because that is what the 1.3 runbook generates (`openssl rand -hex 32`). Exactly 32 bytes are read as raw; otherwise surrounding whitespace is stripped.
- **AAD:** every AAD starts with a versioned domain label (`invest-ai/space-key/v1`, `object-key`, `field`, `file`), so a sealed value of one kind can't be used as another, and fixed-width UUID bytes keep the encodings unambiguous. The AC's components (space_id, object_type, object_id, field) are all included.
- **Stream format:** a 9-byte header (`IAF1`, version, chunk size), then `nonce | ct | tag` per chunk. The chunk AAD binds the header, space, object, a stream `name` (default `content`, so one object can hold several files) and `index (uint64) | final (1 byte)`. An empty file is one empty final chunk, so it's authenticated too. Every chunk is authenticated before it's released; truncation surfaces at the end, so a download that errors part-way must be treated as failed.
- **Sessions:**
  - `create_*` and `shred_*` take the caller's session, so keys commit and roll back with the object.
  - `encrypt_field`/`decrypt_field`/streams use the cache, else a short connection of their own (or an optional `executor`), so they work inside or outside `transaction()`.
  - A newly created key is cached at once, so it can be used before commit.
- **`KeyDestroyed`** covers "never created" as well as "shredded": without tombstones the two can't be told apart.
- **Version check:** a space key wrapped under a KEK version other than the loaded one raises `KekError` (fail closed with a clear message) instead of a confusing `IntegrityError`.
- **Rotation** runs as `app_migrator` (`app_rw` has no UPDATE). It locks `space_keys` in SHARE ROW EXCLUSIVE mode in one transaction, refuses rows at an unexpected version, and requires `new_version > current`. The CLI is `python -m app.crypto.rotate --new-kek PATH [--new-version N]`.
- **Shredding** evicts this process's cache immediately; other processes' cached keys expire within the TTL (≤ 5 min), as ADR-028 allows.
