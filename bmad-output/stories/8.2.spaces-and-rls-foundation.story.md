# 8.2: Spaces and RLS foundation

**Story ID:** 8.2
**Epic:** 8 — Workspaces, Isolation & Encryption
**Slug:** spaces-and-rls-foundation
**Status:** ready-for-dev

## Story

As **compliance**,
I want **every piece of content to belong to a space, with the database itself refusing cross-space reads**,
so that **one missed filter in application code can never become an information-barrier breach**.

## Acceptance Criteria

1. **Migration `8_2_spaces`** creates:
   - `spaces`: `id`, `kind` (`private|workspace`), `owner_user_id` FK `users`, `code_name_enc` (bytea, NULL for private), `retention_days`, `retention_extended_at`, `closed_at`, `created_at`, `updated_at`; a partial unique index giving **one private space per owner**.
   - `space_members`: PK `(space_id, user_id)`, `role` (`owner|member`), `added_by`, `added_at`.

   It also adds the FKs that 8.1 deferred: `space_keys.space_id` and `object_keys.space_id` → `spaces.id`.
2. **RLS foundation:**
   - SQL functions:
     - `app_user_id()`: `current_setting('app.user_id', true)`, NULL when unset.
     - `app_space_ids()`: `STABLE SECURITY DEFINER`; the open spaces the current user belongs to.
   - A migration helper `app.spaces.rls.enable_space_rls(op, table, *, owner_column=None)` runs `ENABLE` + `FORCE ROW LEVEL SECURITY` and creates the standard policy: `space_id = ANY(app_space_ids())`, plus `AND <owner_column> = app_user_id()` when an owner column is given. Every later content migration calls this helper.
   - `spaces` and `space_members` get member-only policies.
   - With **no context set, every policy returns zero rows** (FORCE applies to the table owner too).
3. **AccessContext:**
   - `app.spaces.access.AccessContext(user_id, role, space_ids: frozenset[UUID], grant_id: UUID | None = None)` is frozen.
   - The FastAPI dependency `app.spaces.deps.access_context` builds it from `auth.deps.current_user`, **re-reading memberships on every request** (no caching).
   - `ctx.rls_settings()` returns the mapping for `core.db.transaction(context=...)`.
   - Only `spaces` defines `AccessContext`.
4. **Private space:** `spaces.service.create_private_space(session, user_id)` creates, in the caller's transaction:
   - the space, the owner's membership and the space key (`crypto.keys.create_space_key`);
   - it is idempotent, and records audit `spaces.private_created`.

   `app/spaces/hooks.py` subscribes it to the core event `auth.user_created` (emitted by 2.3 with `session=`).
5. **`GET /api/v1/spaces`:** the caller's private space and open workspaces, as `id`, `kind`, `my_role` and `code_name` (decrypted, members only). `spaces/routes.py` also mounts every `app/spaces/routes_*.py` router, so 8.3 adds a file without editing this one.

## Dev Notes

- **Spaces and enforcement:**
  - `spaces(kind = private | workspace)`; every user gets exactly one private space on creation; workspaces have `space_members(role = owner | member)`.
  - Two enforcement layers: `AccessContext` in every repository function, and RLS with `SET LOCAL app.user_id`.
  - With no context, policies return no rows. `FORCE ROW LEVEL SECURITY` applies to all content tables.

  [Source: architecture.md#ADR-023]
- Membership is re-read on every request, so removal takes effect immediately. Admin code paths run without user context and so see zero content rows by construction. [Source: architecture.md#ADR-023]
- **LOCKED:** no content table without `space_id` and an RLS policy; no repository method without `AccessContext`. [Source: architecture.md#ADR-023]
- Data model fields for `spaces`/`space_members`. [Source: architecture.md#5-data-model]
- `core.db.transaction(context=...)` already sets `app.user_id` / `app.grant_id` with `set_config(..., true)` and rejects unknown keys. [Source: backend/app/core/db.py]
- `app_space_ids()` is SECURITY DEFINER (owned by `app_migrator`, `search_path` pinned), so policies don't recurse through `space_members`' own RLS. A closed space (`closed_at` set) drops out at once. [Inference]
- Code names are encrypted (ADR-028 list): encrypt them with `crypto.fields` under an object key `(space, space_id)`. 8.3 sets them; 8.2 only decrypts. [Source: architecture.md#ADR-028]
- **Retention:** `retention_days` defaults to 30 (FR-052, configurable 7–90 later by admin settings). [Source: prd.md#FR-052]

## Testing

- **Approach:** integration tests with `pg` as `app_rw` (RLS applies), plus a throwaway table created with `enable_space_rls` in the test.
- **Per-AC verification:**
  - AC #1 → migration up/down; a second private space for the same owner is rejected; the key-table FKs reject an unknown `space_id`.
  - AC #2 → no context → 0 rows from every policy table; user A's context sees A's rows only; FORCE: the `app_migrator` owner also sees 0 without context; closed spaces vanish.
  - AC #3 → membership removed mid-test → the next `access_context` excludes the space; `rls_settings` keys are accepted by `transaction()`.
  - AC #4 → emitting `auth.user_created` inside a transaction creates the space, membership and space key; a rollback leaves nothing; calling twice is a no-op.
  - AC #5 → `GET /spaces` as A excludes B's spaces; an unauthenticated request → 401; the code name of a space the caller isn't a member of never appears.
- **Edge cases:** user deleted (FK behaviour documented); `app.user_id` set to a malformed UUID (policy returns no rows, no error leak).

## Learnings from Previous Stories

- **Crypto API (8.1):**
  - `crypto.keys.create_space_key(session, space_id)`, `create_object_key(session, space_id, type, id)` → `KeyRef`, `fields.encrypt_field/decrypt_field(ref, field, ...)`.
  - Creating a key needs the KEK loaded.
- Default privileges give `app_rw` full DML on new tables. REVOKE what a table must not allow (7.1 and 8.1 did). (from 7.1)
- Alembic autogenerate ignores runtime audit partitions via `include_name` in `migrations/env.py`. (from 7.1)
- Core events: `core.events.subscribe(name, fn)`. Subscribers run in order and exceptions propagate (fail closed). (from 1.2)
