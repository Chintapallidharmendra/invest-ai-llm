# 8.3: Deal workspaces API

**Story ID:** 8.3
**Epic:** 8 — Workspaces, Isolation & Encryption
**Slug:** deal-workspaces-api
**Status:** ready-for-dev

## Story

As a **deal lead**,
I want **to create a code-named deal workspace and control exactly who is in it**,
so that **my team can share documents while the deal stays behind its information barrier**.

## Acceptance Criteria

1. **Create:** `POST /api/v1/spaces` `{code_name}` (role `user`) creates a `workspace` space with the caller as `owner`, its space key, and `code_name_enc` (encrypted, ≤ 80 chars, trimmed). Returns `201`.
2. **Rename:** `PATCH /api/v1/spaces/{id}` `{code_name}` (owners only). Code names are returned only to members; to anyone else the space doesn't exist (404).
3. **Members:**
   - `GET /api/v1/spaces/{id}/members` (members).
   - `POST /api/v1/spaces/{id}/members` `{username, role: member|owner}` (owners only). It resolves an **exact, active, role `user`** username, so admins and compliance can never be members; otherwise 404 `user_not_found`.
   - `DELETE /api/v1/spaces/{id}/members/{user_id}` (owners; or a member removing themselves).
   - The **last owner cannot be removed or demoted** (409).
   - A removed member's next request to anything in the space is a 404.
4. **Close:** `DELETE /api/v1/spaces/{id}` (owners) requires `{confirm: true}`.
   - It sets `closed_at`, so the space leaves `app_space_ids()` at once.
   - It records `spaces.workspace_closed`, and the deletion itself is queued for the 7.4 delete pipeline (a `lifecycle` job when that type is registered; until then `closed_at` alone hides everything).
   - Private spaces can't be closed (409).
5. **Audit (metadata only):** `spaces.workspace_created`, `spaces.workspace_renamed`, `spaces.member_added`, `spaces.member_removed`, `spaces.member_role_changed`, `spaces.workspace_closed`. These carry IDs and enums only, never code names.

## Dev Notes

- **FR-040:**
  - Only owners and co-owners manage members, and changes are audited.
  - A removed member loses access on the next request, including to outputs they generated from workspace documents.
  - Names are visible only to members; the owner can close the workspace, which leads to permanent deletion.

  [Source: prd.md#FR-040]
- Membership is re-read every request; not accessible = 404. [Source: architecture.md#ADR-023]
- **Paths:** `POST /spaces`, `PATCH /spaces/{id}`, `DELETE /spaces/{id}` (owner; confirm), `GET/POST /spaces/{id}/members`, `DELETE /spaces/{id}/members/{user_id}`. [Source: architecture.md#6-api-specifications]
- Workspace code names are among the encrypted fields. [Source: architecture.md#ADR-028]
- Admins have no content access, so only role `user` can be members. [Source: prd.md#FR-005]
- Q18 (move/copy between workspaces) is open; nothing here moves documents (that is 9.x). [Source: addendum.md#open-questions]

## Testing

- **Approach:** API tests with three users (owner, member, outsider) and an admin.
- **Per-AC verification:**
  - AC #1 → the code name is stored encrypted (no plaintext in `spaces`); a space key exists.
  - AC #2 → an outsider GET/PATCH → 404; the code name is absent from outsider responses.
  - AC #3 → adding an admin → 404; last-owner removal → 409; removed member → 404 on the next request.
  - AC #4 → closed space absent from `GET /spaces` and RLS; closing a private space → 409.
  - AC #5 → `assert_no_content` on all events.
- **Edge cases:** an owner demoting themselves while another owner exists; re-adding a removed member; concurrent last-owner removals (serialised; one gets 409).
