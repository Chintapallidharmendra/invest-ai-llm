# 9.3: OCR for scanned pages

**Story ID:** 9.3
**Epic:** 9 — Document Processing
**Slug:** ocr-scanned-pages
**Status:** ready-for-dev

## Story

As a **banker**,
I want **scanned or signed PDF pages to be read with OCR**,
so that **a scanned term sheet or signed SPA can be searched and cited like any other document, with OCR'd text clearly marked**.

## Acceptance Criteria

1. **Schema (additive, still `schema_version` 1):**
   - `TextItem.ocr: bool = False`;
   - `Limits.max_ocr_pages = 300`, `Limits.ocr_pages_per_call = 20`, `Limits.ocr_cpu_s = 300`, `Limits.ocr_wall_s = 360.0` (a request can only lower them, as today);
   - `OcrPage {locator, text: list[TextItem], mean_confidence: float}` and `OcrResult {schema_version, ok: true, pages: list[OcrPage]}`.
2. **Cap at parse time:** `POST /parse` on a PDF whose `needs_ocr` list is longer than `max_ocr_pages` returns `ParseFailure{code: limit_exceeded, detail: "ocr_pages"}`.
3. **`POST /ocr`** (multipart: `file` = the PDF, `pages` = JSON list of `p.N` locators, ≤ `ocr_pages_per_call`, optional `limits`):
   - renders each listed page with pypdfium2 (≈ 200 dpi, grayscale) and runs **RapidOCR (onnxruntime, CPU, English)** on it;
   - returns `OcrResult` with one `OcrPage` per requested page, `TextItem`s in reading order (top-to-bottom, left-to-right lines grouped into paragraphs), `kind=text`, `locator="p.N"`, `ocr=true`, `order` restarting at 0 per page (the caller re-sequences);
   - a page with no recognised text returns an empty `text` list (not an error);
   - bad locators, more than `ocr_pages_per_call` pages, or a non-PDF → 422 `ParseFailure` (`invalid_request`).
4. **Same sandbox as `/parse`:** OCR runs in the rlimited child process (`ocr_cpu_s`, `ocr_wall_s`, address space), no network, scratch on tmpfs; a breach returns `ParseFailure{code: limit_exceeded | timeout}`; the service log line carries counts and timings only (`pages`, `items`, `ms`), never text.
5. **Offline models:** the RapidOCR det/rec/cls ONNX models load from the installed package or a staged path (`RAPIDOCR_MODEL_DIR`) with no network access. If the locked wheel does not bundle them, they are added to `deploy/models/manifest.yaml` with SHA-256 and mounted read-only in `compose.parser.yml`.
6. **Performance:** on the dev machine, a 200-dpi A4 page of typed English text OCRs in ≤ 15 s CPU (`@pytest.mark.perf`), and a planted line (e.g. "Consideration: INR 1,250 crore") is recognised verbatim.

## Dev Notes

- **ADR-027 step 2:** pages without a text layer go to OCR via RapidOCR (CPU, English), with segments marked `ocr=true` (FR-044). The parser has no network, 4 GB memory, read-only root, tmpfs scratch. [Source: architecture.md#adr-027-document-ingestion-pipeline-supersedes-adr-014]
- **FR-044:** pages with no text layer are OCR'd automatically (English); OCR'd text is marked so citations note "OCR"; at most 300 OCR pages per document, larger scans rejected with an explanation. [Source: prd.md#fr-044-ocr-for-scanned-pages--should-assumed]
- **NFR-024:** OCR ≤ 15 s per page. [Source: prd.md#nfr-024-processing-performance--should-performance]
- **NFR-025:** parsers run with resource limits and no network. [Source: prd.md#nfr-025-spreadsheet-and-file-safety--must-security]
- **Why a separate `/ocr` call:** a 300-page scan at up to 15 s/page cannot fit the 120 s CPU / 180 s wall budget of one `/parse`. Batches of ≤ 20 pages, each in its own sandbox, keep every call bounded and let 9.4 resume after a restart from the last committed batch. [Inference, from ADR-027 "idempotent and resumable" and 9.2 limits]
- **Direct RapidOCR, not Docling's OCR stage:** `do_ocr` stays `False`. Docling's OCR would re-run layout on every page and may fetch models at runtime; calling `rapidocr_onnxruntime` on pypdfium2-rendered pages is bounded and offline. [Inference]
- **Only `documents.ingestion` talks to the parser** (9.4 will call `/ocr`). Masking and the injection scan of OCR text happen in the worker (9.5), like any other text. [Source: architecture.md#adr-038-module-boundaries-v2-supersedes-adr-001]
- **Dependencies:** `rapidocr-onnxruntime` and `pypdfium2` are already in `parser/pyproject.toml`; don't edit the dependency list. [Source: epics.md#shared-file-conventions-parallel-safety-rules-for-every-story]

## Testing

- **Approach:** parser unit tests + service tests through the HTTP app (as in `test_service.py`); perf test marked `perf`.
- **Fixtures:** generate image-only PDFs in a fixture (render known text with Pillow into a page image, embed with pypdfium2) — one page, a 3-page mix (text, scan, text), a blank scan, and a synthetic 301-scan-page PDF built from one repeated image.
- **Per-AC verification:**
  - AC #1 → model round-trips; `capped` can lower but not raise the OCR limits.
  - AC #2 → 301 scan pages → `limit_exceeded`/`ocr_pages`.
  - AC #3 → planted text recognised on the scan page with `ocr=true`, `locator="p.2"`; blank page → empty list; 21 pages or `p.0` → 422.
  - AC #4 → a forced low `ocr_cpu_s` returns `limit_exceeded`; the log line has no recognised text (search the captured log for the planted string).
  - AC #5 → run OCR with sockets blocked (monkeypatched `socket.socket`) and it still loads.
  - AC #6 → perf marker measures per-page CPU.
- **Edge cases:** rotated page (90°) — record what RapidOCR does, don't fix; very large page size (render capped by pixel count); password-free but corrupt PDF → `corrupt_file`.

## Learnings from Previous Stories

- **9.2:** `RLIMIT_CPU` counts every thread; set `OMP_NUM_THREADS` (and onnxruntime intra-op threads) to 4 in the child so CPU time stays predictable.
- **9.2:** the service returns 200 `ParseResult` / 422 `ParseFailure`, and `detail` is a fixed, content-free word.
- **9.2:** `make test` doesn't run parser tests; run them with `uv run pytest` inside `parser/`.
- **9.2:** the Docling models are staged at `DOCLING_ARTIFACTS_PATH`; follow the same manifest format if RapidOCR models need staging.
